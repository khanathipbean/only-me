# ขั้น 3 — สิทธิ์แก้ไขได้จากหน้าเว็บ — Plan

Goal: ติ๊ก checkbox ในหน้า Roles & Permissions แล้วสิทธิ์เปลี่ยนจริงทั้งระบบ

Current vs desired (Diff):
- ตอนนี้: `rolesFor(key)` อ่านอาเรย์คงที่จาก `rbac.ts` แบบ synchronous
  ทุกการตรวจสิทธิ์ (145 จุด) เดินผ่านมันแล้ว
- ต้องการ: `rolesFor` อ่านค่าที่ถูกแก้จากฐานข้อมูลทับค่าในโค้ด

เคาะกับผู้ใช้แล้ว:
1. อนุญาตให้ทำ migration บน production
2. logic กันล็อกเอาต์ ให้ผมออกแบบ
3. ตารางว่าง = ใช้ค่าในโค้ด เก็บเฉพาะสิ่งที่ถูกแก้
4. กัน capability ที่พังแล้วกู้ไม่ได้ไว้ไม่ให้แก้

## กติกากันล็อกเอาต์ (ข้อ 2 + 4)

หลักคิด: **ต้องมีทางกลับเข้าระบบเสมอ** ทางกลับมีทางเดียวคือหน้า Settings →
Users ฉะนั้น

- `install.settings` และ `install.users` **แก้ไม่ได้** ตรึงไว้ที่ ADMIN
  เสมอ ทำเครื่องหมาย `fixed: true` ในแค็ตตาล็อก หน้าเว็บวาดเป็น checkbox ที่
  กดไม่ได้พร้อมคำอธิบาย และ**ฝั่งเซิร์ฟเวอร์ปฏิเสธ**ทุกคำสั่งที่อ้างถึงสองตัวนี้
  — การซ่อนปุ่มไม่ใช่การกั้น ซึ่งเป็นกฎเดิมของโปรเจกต์นี้อยู่แล้ว
- เมื่อสองตัวนี้ตรึงแล้ว ความผิดพลาดอื่นทุกแบบกู้คืนได้จากหน้าเว็บ จึง**ไม่ต้อง**
  ห้ามอย่างอื่น — รวมถึงการติ๊กออกจนไม่มี role ไหนถืออยู่เลย ซึ่งอาจเป็นสิ่งที่
  ตั้งใจ (เช่น ไม่ให้ใครส่งออกข้อมูลได้)
- `install.project-create` แก้ได้ เพราะถึงไม่มีใครสร้าง Project ได้ ก็ยังเข้า
  ระบบและแก้สิทธิ์กลับได้

Out of scope / do NOT touch (Fence):
- ค่าคงที่ใน `rbac.ts` ยังเป็นค่าเริ่มต้น ไม่ลบ ไม่ย้าย
- ตารางสิทธิ์เก็บเฉพาะส่วนต่าง ไม่ seed ข้อมูลตอน migrate
- ไม่แตะ `ProjectRole` enum — ไม่เพิ่ม role ใหม่ในขั้นนี้

Risks & unknowns:
- `rolesFor` ต้องกลายเป็น async ซึ่งกระทบทุกผู้เรียก แต่ขั้น 2 ทำให้เกือบทุกจุด
  อยู่ในฟังก์ชัน async อยู่แล้ว — `withCapability` เป็นจุดเดียวที่ตอนนี้เรียก
  ตอนโหลดโมดูล ต้องย้ายไปเรียกตอนรับ request
- ต้องไม่ยิง DB ซ้ำ 5 ครั้งต่อหนึ่งหน้า — อ่านทั้งตารางครั้งเดียวต่อ request
  (ตารางเล็กมาก อย่างมาก 24 × 5 แถว)
- ถ้าอ่านตารางล้มเหลว ต้อง fall back เป็นค่าในโค้ด ไม่ใช่ปฏิเสธทุกคน

## Steps
1. schema: `RolePermission { role, capability, allowed }` unique(role,capability)
   — verify: `migrate diff` อ่านได้ ไม่มีอย่างอื่นเปลี่ยน
2. `rolesFor` เป็น async อ่าน override ทับค่าเริ่มต้น + cache ต่อ request
   — verify: unit test ว่าทับถูก และ fall back เมื่ออ่านไม่ได้
3. ไล่แก้ผู้เรียกให้ await — verify: tsc + ชุดเทสต์เดิมต้องเขียวทั้งหมด
4. server action บันทึกการติ๊ก + ปฏิเสธ capability ที่ `fixed`
   — verify: unit test ว่าปฏิเสธจริง
5. หน้าเว็บ: checkbox ใช้งานได้ + ปุ่ม Save + ตัวที่ตรึงไว้กดไม่ได้
   — verify: browser test ติ๊กแล้วบันทึกแล้วสิทธิ์เปลี่ยนจริง
6. migration บน production (ได้รับอนุญาตแล้ว) — verify: ตรวจตารางหลัง deploy
