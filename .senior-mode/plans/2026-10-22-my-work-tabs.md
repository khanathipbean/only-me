# My Work: แท็บ ประวัติ และ By Assignee — Plan

Goal: My Work ตอบได้ทั้ง "อะไรรออยู่" และ "อะไรผ่านไปแล้ว" และบอกได้ว่างาน
ซ่อมทั้งหมดกระจายอยู่กับใคร

Current vs desired (Diff):
- ตอนนี้หน้านี้แสดงเฉพาะงานที่ยังค้าง พอ Tester บันทึก Pass การ์ดหายทันที
  และไม่มีที่ไหนให้ย้อนดู → ต้องมีแท็บประวัติ
- ตอนนี้ By Assignee อยู่บน Dashboard ซึ่งเป็นบล็อกเดียวที่พูดเรื่อง "คน"
  ท่ามกลางบล็อกที่พูดเรื่อง "การทดสอบ" → ย้ายมาที่นี่

## ไม่มีอะไรหายไปเลย — นี่คือเรื่องสำคัญที่สุดในแผนนี้

`workOpsForResult` ตอนปิดวงจรทำสามอย่าง: `workState = null`, `dueAt = null`
และ **เก็บ `assigneeId` ไว้** พร้อมเขียน `WorkEvent` ที่ `toState = null`

แปลว่าประวัติการส่งต่อทั้งหมดอยู่ในฐานข้อมูลครบอยู่แล้ว สิ่งที่ "ลบ case ออก
จาก Dev" คือ **มุมมอง** ไม่ใช่ข้อมูล — `listMyWork` กรอง `workState != null`
ทิ้งไป

  ไม่ต้องแก้ schema เลย ไม่ต้อง migration ไม่ต้องแตะ production

## แท็บคืออะไร และ By Assignee ไม่ใช่แท็บ

หน้านี้มี filter อยู่แล้วหนึ่งแกน: **ของใคร** (มอบหมายให้ฉัน / ฉันส่งต่อ /
ทั้งโปรเจกต์) แท็บคือแกนที่สอง: **ยังค้าง หรือ จบแล้ว**

ส่วน By Assignee ไม่ใช่ทั้งสองแกน มันคือ "ของเดิมนับอีกแบบ" — สรุปของสิ่งที่
filter กับแท็บเลือกมาแล้ว การเอาไปซ่อนหลังแท็บคือการเอาตัวเลขที่ให้บริบทกับ
รายการ (3 อยู่กับคน 612 ไม่อยู่กับใคร) ไปไว้หลังคลิก

เสนอ: **สองแท็บ Open / Finished** และ By Assignee เป็นแถบสรุปเหนือทั้งคู่

ทางเลือกที่ผู้ใช้เสนอ — แท็บ "My Work" กับ "By Assignee" แล้วเอาประวัติไปไว้
ในแท็บหลัง แยกรายคน — ก็อ่านรู้เรื่อง แต่ทำให้ "ประวัติ" เข้าถึงได้เฉพาะเมื่อ
มองผ่านแว่น "คน" ซึ่ง Dev ที่อยากดูว่าตัวเองแก้อะไรไปบ้างต้องเดินอ้อม

## แท็บ Finished แสดงอะไร

หนึ่งแถวต่อหนึ่งครั้งที่วงจรปิด (`WorkEvent` ที่ `toState = null`):

  case · ใครถือ · ปิดเมื่อไร · ผลที่ปิดมันคืออะไร · ใช้เวลากี่วันทำการ

"ใช้เวลา" คำนวณจากคู่ของมัน — `ASSIGNED` ที่อยู่ก่อนหน้าในกรณีเดียวกัน ไม่ต้อง
เก็บคอลัมน์เพิ่ม

กติกาที่ต้องเขียนไว้บนหน้า: **ทดสอบซ้ำแล้วยัง Fail ไม่ปิดวงจร** มันเด้งกลับ
เป็น ASSIGNED ดังนั้น "Finished" แปลว่า "ทดสอบซ้ำแล้วจบ" ซึ่งเกือบทั้งหมดคือ
"แก้แล้วผ่าน" — ส่วน case ที่วนสองรอบจะปรากฏสองแถว ถูกต้องแล้วเพราะมันถูก
ส่งต่อสองครั้งจริง ๆ

## กับดักที่ต้องระวัง: filter "ฉันส่งต่อ" บนแท็บ Finished

`actorId` ของ event ที่ปิดวงจรคือ **Tester ที่บันทึกผล** ไม่ใช่คนที่ส่งงานออก
ไป ถ้าเขียน `actorId = ฉัน` ตรง ๆ แท็บนี้จะกลายเป็น "ที่ฉันทดสอบซ้ำ" ซึ่งเป็น
คนละคำถาม

ต้องอ่านจาก event ตอน `ASSIGNED` ของ case นั้นแทน แบบเดียวกับที่ `scopeFilter`
ทำอยู่แล้ว รวมทั้งข้อที่ว่า actor ต้องไม่ใช่ assignee เอง

## แถบ By Assignee

ย้ายมาจาก Dashboard ทั้งก้อน และเปลี่ยนประชากรที่นับ:

  Dashboard เดิม   ทุก case ที่มี assigneeId ไม่ว่างานซ่อมจะจบไปแล้วหรือไม่
  ที่นี่            เฉพาะที่ตรงกับแท็บและ filter ที่เลือกอยู่

เลขเดิมบน Dashboard รวม case ที่ปิดงานไปแล้วด้วย เพราะปิดวงจรแล้วยังเก็บ
assignee ไว้ — มันจึงเป็นเลขที่พูดไม่ตรงความจริงกว่า

Dashboard เหลือ 3 บล็อกใน 3 คอลัมน์ ปัญหา layout ที่เพิ่งจัดใหม่หายไปเอง และ
การจับคู่ Priority กับ Assignee ไว้คอลัมน์เดียวกันจะถูกถอนออก

เสีย drill-down รายคนบน Dashboard — ชดเชยด้วยการให้ชื่อคนบนแถบนี้กดได้ แล้ว
กรองรายการบนหน้านี้เอง ซึ่งตอบคำถามตรงกว่าอยู่แล้ว

## ตัวควบคุมแท็บ

Members วาด segmented control ไว้ใน JSX ของหน้าตัวเอง ไม่ใช่คอมโพเนนต์ร่วม —
นี่คือที่ใช้ที่สอง ซึ่งเป็นจุดที่ควรแยกออกมา `src/components/ui/ViewTabs.tsx`
และให้ Members ใช้ตัวเดียวกัน จะได้ไม่มีสองตัวที่ค่อย ๆ ต่างกัน

เก็บเหตุผลเดิมไว้ทั้งหมด: ไม่ใส่ `role="tablist"`/`"tab"` เพราะมันคือลิงก์ไป
สองที่อยู่ ไม่ใช่ widget ที่สลับ panel และตอบปุ่มลูกศร — `aria-current` คือคำ
ที่ถูกต้องสำหรับ "คุณอยู่หน้าไหน"

Out of scope / do NOT touch (Fence):
- ไม่แก้ schema และไม่แตะ production — ทุกอย่างอ่านจาก `WorkEvent` ที่มีอยู่
- ไม่แตะกติกาผลการทดสอบ (`workOpsForResult`) ที่เพิ่งลงตัว
- ไม่แตะหน้า Members นอกจากเปลี่ยนให้ใช้คอมโพเนนต์ที่แยกออกมา

Risks & unknowns:
- แท็บ Finished โตไม่มีเพดาน ต้อง paginate จริงด้วย page/size ไม่ใช่ slice
- `WorkEvent` ไม่มี index บน `toState` และการกรอง "ใน project นี้" วิ่งผ่าน
  relation — ตอนนี้ production มี 0 แถวจึงไม่เป็นปัญหา แต่ถ้าช้าขึ้นมาทางแก้คือ
  index `[toState, occurredAt]` ซึ่งเป็น migration เพิ่มอย่างเดียว
- การจับคู่ ASSIGNED กับ event ที่ปิดวงจรต้องทำในหน่วยความจำจาก event ของ
  case นั้น ระวังกรณีที่มีการส่งต่อซ้อนกันหลายรอบ
