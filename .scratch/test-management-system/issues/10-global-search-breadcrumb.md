# 10: Global Search + Breadcrumb

**What to build:** A global search box finds Projects, Scenarios, Test Groups, and Test Cases by name/code/ID from anywhere in the app, and a breadcrumb shows the user's current position in the hierarchy, preserving prior search/filter state when navigating back up.

**Blocked by:** 05 (Test Case CRUD)

**Status:** ready-for-agent

- [x] `GET /api/search?q=...`: searches Project (name/code), Scenario (name/id), Test Group (name), Test Case (name/id) scoped to Projects the caller is a member of; each result includes its type, Project name, and hierarchy position
- [x] Global Search UI: search box available from any page, results list showing type/Project/position, clicking a result navigates to its detail, clear "no results" state
- [x] Breadcrumb component: renders the current path (e.g. `Projects > Project A > Scenario A > Navigation > TC-001`) on every detail/list page in the hierarchy; each segment is clickable to navigate up
- [x] Navigating up via the breadcrumb restores the previous page's search term, filters, and list page where the target page supports them (e.g. returning to a Test Group's Test Case list keeps its prior filter)
- [x] Tests: search across all four entity types returns correct type/position, search respects project membership (no cross-tenant leakage), breadcrumb renders the correct path at each level, breadcrumb back-navigation restores prior list state

## Comments

Global Search: `src/lib/search.ts` runs the four entity queries in parallel, scoped to `ProjectMember` rows for the caller — a non-member sees nothing regardless of query, tested explicitly. `GET /api/search` (`src/app/api/search/route.ts`) is the ticket's required JSON contract, tested directly; the actual UI (`src/app/search/page.tsx` plus a `<form action="/search">` rendered in the root layout whenever a session exists) calls `searchAll` directly rather than fetching that route, matching this app's established plain-HTML-form/server-rendered-list style (no client-side fetch for a simple list) — the API route exists as its own deliverable per the ticket's own first bullet, not because the UI needs it as a client.

Breadcrumb — a real design bug caught by review and fixed before commit: the first version's detail-page breadcrumbs (Scenario/Test Group/Test Case) skipped the intermediate list-page segment entirely, to visually match the spec's shorthand example (`Projects > Project A > Scenario A > Navigation > TC-001`, User Story 60). That made this ticket's own explicit requirement ("returning to a Test Group's Test Case list keeps its prior filter", line 12) architecturally unreachable — no breadcrumb segment ever pointed at a list page, so the sessionStorage-based restoration in `Breadcrumb.tsx` had no live path to trigger. Fixed by having `src/lib/breadcrumb.ts`'s builders include the list-page segment as a clickable link on every detail page (e.g. Test Case detail is now `Projects > Project A > Scenarios > Scenario A > Test Groups > Navigation > Test Cases > TC-001`) — a deliberate, documented deviation from the spec's abbreviated example, made because this ticket's own concrete acceptance criterion is unambiguous and testable while the User Story line is illustrative prose. `src/app/projects/page.tsx` also got a minimal one-segment Breadcrumb (`Projects`, non-clickable) so the Projects list's own filter state gets recorded and is restorable from anywhere that links back to `/projects` — it was the one hierarchy-root page the first pass missed.

Restoration mechanism itself: `Breadcrumb.tsx` records the current page's query string into `sessionStorage` keyed by pathname on every render, and any ancestor link looks up whether the page it points to has a stored query string, appending it if so. The lookup is deferred to run only after mount (nested inside a `.then()` inside the effect) specifically so the first client render matches the server-rendered bare href — avoiding both a hydration mismatch and the strict `react-hooks/set-state-in-effect` lint rule this repo enforces (same `.then()`-deferral technique used in `DashboardView.tsx`).

Not automated: the sessionStorage record/restore behavior itself has no test, for the same reason ticket 09's expand/collapse state wasn't testable — this repo's Vitest setup (`environment: "node"`, no jsdom/React Testing Library) only supports route-handler and pure-function tests, not DOM/browser-API interaction. `tests/breadcrumb.test.ts` covers the one part that is a pure function: each builder's segment/label/href output at every hierarchy level, now including the corrected list segments.

Accepted, not fixed: Standards review flagged that each of the 6 breadcrumb-carrying pages now fires 1-2 extra `findUnique`-by-id queries (for ancestor Project/Scenario names) that didn't exist before. These are cheap indexed primary-key lookups on a low-traffic internal tool, and no caching/batching layer exists anywhere else in this codebase (the Dashboard and Audit Trail routes already run multiple independent queries per request) — adding one here for breadcrumb labels alone would be a bigger, unrequested architectural addition, so this was left as-is.

Scope trim: the first version's `searchAll` also matched a Project by exact `id`; removed, since the ticket lists only "Project (name/code)" — a Project's user-facing identifier is its `code`, unlike Scenario/Test Case which use their system-generated id as a reference (spec User Story 22).

Unrelated but necessary, carried in this commit: `src/lib/enums.ts` was added to fix a real bug in ticket 09's shipped code (a client component transitively importing `@/lib/prisma` via `src/lib/dashboard.ts`, breaking a clean `next build`) — caught while starting this ticket; documented in both `09-project-dashboard.md` and here since the fix lives in files this ticket also touches.

Reviewed via the proper two-axis parallel-subagent process this time (ticket 09 fell back to self-review after both review agents failed on an org-wide API spend cap). Both agents' findings were addressed above except the accepted query-count trade-off. Re-verified after fixes: 81 tests passing, typecheck/lint clean, and a **cache-cleared** `next build` (the ticket 09 incident showed a cached build can mask a real bundling failure) passing with `/search` and every breadcrumb-bearing route present.
